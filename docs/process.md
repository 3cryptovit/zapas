# Процесс: как шла работа и что из этого следует

Разбор пути по проекту: где работа переделывалась, откуда брались
ошибки и какой порядок работы их сокращает.

Полезен не пересказом событий, а второй частью — классификацией
ошибок. Все примеры настоящие, из этого проекта.

---

### Что показывает эта таблица

Переделок одиннадцать, и десять из них в последней трети. Ядро -
схема, изоляция, формулы прогноза, транзакции склада - держалось с
первого раза и почти не правилось.

Ломалось всё на краях:

- среда, которой не оказалось такой, как в документе;
- доставка: nginx, сертификаты, systemd, CI;
- проверка: способ убедиться, что работает, сам оказывался сломан.

Вывод, неочевидный в начале: время уходит не на бизнес-логику. На неё
есть формулы из ТЗ и табличные тесты. Время уходит на стыки с
реальностью, и дисциплина нужна именно там.

## 2. Откуда берутся ошибки

Все дефекты проекта раскладываются на шесть классов. Для каждого -
корень и то, что его ловит.

### Класс A. Среда оказалась не такой, как в документе

| Случай | Чем обернулось |
|---|---|
| ТЗ предполагало выделенный сервер 2 vCPU / 4 ГБ под Docker | Переписан весь подход к размещению |
| `COPY FROM` по 7.1 | PostgreSQL не поддерживает его для таблиц с RLS |
| `time.LoadLocation` в distroless | Нет `/usr/share/zoneinfo`, день тенанта сломался бы только в проде |
| `postgres` как сервис в CI | Init-скрипты не выполняются, ролей нет, тесты зелёные только локально |
| `http2 on;` в nginx | Директива появилась в 1.25, на сервере старее |
| Репозиторий на GitHub | CI был написан под GitLab |

**Корень.** Документ о мире принимался за мир. ТЗ, документация
библиотеки и память о том, как обычно бывает, - это гипотезы, а не факты.

**Что ловит.** Команда, выполненная на целевой машине до того, как
написан код. Пять минут ssh в начале девятого этапа сэкономили бы день.

### Класс B. Немой отказ: код ответа правильный, результат нет

| Случай | Что показывали приборы |
|---|---|
| `alias` в regex-локации nginx | `/app/` отдаёт 200, все скрипты 403. Белый экран |
| Адрес без слеша на конце | Браузер честно переходит и показывает лендинг вместо кабинета |
| k6 после потери сессии | Пороги зелёные: дашборд 1 мс - это скорость ответа 401 |
| Ротация бэкапа | Скрипт падал с кодом 2 после того, как успешно снял дамп |
| `scp` из служебного контейнера | Код возврата 0, файл не записан |

**Корень.** Проверялся заместитель результата, а не результат. Код
ответа - не то же самое, что работающая страница. Зелёный порог
латентности - не то же самое, что работающий сценарий.

Этот класс самый дорогой. Он не даёт ни записи в логе, ни всплеска в
метрике: приборы показывают норму. Обнаруживает его человек, который
открыл и посмотрел.

**Что ловит.** Проверка наблюдаемого результата: браузер для страницы,
поиск по содержимому для ответа, порог на долю успешных ответов рядом с
порогом на скорость.

### Класс C. Шов между модулями

| Случай | В чём дело |
|---|---|
| Приёмка не обнуляла «в пути» | Пересчёт статуса шёл до смены статуса заказа |
| Симулятор писал расход из будущего | Фиксированное 14:00 против текущего виртуального времени |
| `/me` и `/auth/logout` вне middleware | В роутере выглядит правдоподобно |
| Приёмка брала системные часы | Проверка склада сравнивает с часами тенанта |

**Корень.** Каждый модуль по отдельности прав. Не определён контракт
между ними: кто владеет «сейчас», в какой момент меняется статус, что
считается временем события.

**Что ловит.** Сквозной тест, проходящий весь цикл, а не юнит-тест
модуля. Три бага из четырёх нашли именно такие тесты.

### Класс D. Документ, написанный по памяти о коде

| Случай | Что написано | Что в коде |
|---|---|---|
| Причины списания в OpenAPI | spoilage, breakage, staff | spoiled, broken, expired, tasting |
| Архивация позиции | 200 с телом | 204 |
| Импорт без ошибок | 200 | 201 |
| Раннбук отката | `migrate down` | В проде запрещён кодом |
| Раннбук про демо | IP клиента в журнале приложения | Его пишет nginx |

**Корень.** Документация писалась, глядя на код, а не на его поведение.
Между «я помню, как это работает» и «вот ответ сервера» помещается
ровно этот класс ошибок.

Показательно, что фронтенд был прав везде: он ходит в настоящий API, и
неправда там не выживает.

**Что ловит.** Документ, собранный из живого ответа. В пределе -
автоматическая сверка ответов со схемой.

### Класс E. Вырожденный вход

| Случай | Что не учли |
|---|---|
| Обрезка выбросов при IQR = 0 | Ровный ряд - ровно тот случай, ради которого она нужна |
| CSV в CP1251 | Excel на русской Windows сохраняет так по умолчанию |
| Пустой каталог недельных копий | Первый день работы бэкапа |

**Корень.** Тестовые данные придумывал тот же, кто писал код, и
придумывал их правдоподобными. Правдоподобные данные проходят всегда.

**Что ловит.** Список крайних случаев, составленный до реализации и
обязательный: пусто, ноль, один, вырожденное, чужая кодировка,
враждебный ввод.

### Класс F. Инструментарий

CRLF в файлах Go, конвертация путей в Git Bash, кодировка PowerShell,
забитый диск, порванный кеш модулей, банка cookie с возвратом каретки в
собственном проверочном скрипте.

**Корень.** Разработка под Windows, сборка в Linux-контейнере,
развёртывание на Ubuntu. Три среды, три набора умолчаний.

**Что ловит.** Правила, закреплённые в файлах, а не в голове:
`.gitattributes`, контейнер для всех команд, зафиксированные версии.

### Итог

| Класс | Доля | Чем закрывается |
|---|---|---|
| A. Среда | около четверти дефектов | Проверка предпосылок командой до кода |
| B. Немой отказ | около шестой части, но самый дорогой | Проверка наблюдаемого результата |
| C. Шов | около восьмой части | Сквозные тесты |
| D. Документ по памяти | около шестой части | Документ из живого ответа |
| E. Вырожденный вход | около десятой части | Список крайних случаев до реализации |
| F. Инструментарий | около пятой части времени | Правила в файлах |

## 3. Порядок работы

Правило: **одна сессия работы = одна законченная задача**, и её
результат лежит в файлах, а не в чьей-то памяти. Открытый через неделю
репозиторий должен отвечать на вопросы «что сейчас в работе», «почему
так сделано» и «что уже ломалось» без единого вопроса вовне.

### Память проекта

| Файл | Что помнит | Когда меняется |
|---|---|---|
| [CONVENTIONS.md](../CONVENTIONS.md) | Правила и запреты | Редко, при новом правиле |
| [spec.md](spec.md) | Требования, формулы, критерии приёмки | При изменении требований |
| [adr/](adr/) | Архитектурные решения с отвергнутыми вариантами | При решении, которое дорого отменять |
| [features/](features/) | Задачи: цель, крайние случаи, план проверки, статус | Каждая задача |
| [journal.md](journal.md) | Что сломалось и почему | Каждый заметный случай |
| [acceptance.md](acceptance.md) | Сценарии ручной проверки | При новой функциональности |
| [api/openapi.yaml](api/openapi.yaml) | Контракт API | При изменении ручки |
| [runbooks/](runbooks/) | Что делать, когда сломалось | При новом способе сломаться |

Ни один из этих файлов не пересказывает код. Код и так виден. Они
хранят то, чего в коде нет: почему выбрано так, что уже пробовали, что
проверять руками.

### Задача

Единица работы - файл `docs/features/<имя>.md` по
[шаблону](features/_template.md). Заводится **до** кода.

Ключевые разделы шаблона:

- **Предпосылки** - утверждения о среде и команда, которой каждое
  проверено. Класс A закрывается здесь.
- **Крайние случаи** - список, составленный до реализации. Класс E.
- **Как проверю** - конкретный наблюдаемый результат, а не «тесты
  зелёные». Класс B.
- **Решения** - что выбрано и от чего отказались. Спустя месяц это
  единственное, что объясняет код.
- **Оценка и факт** в часах. Расхождение - полезная информация о себе.

### Порядок сессии

**1. Загрузить контекст.** Читается не весь репозиторий, а:
CONVENTIONS.md, файл задачи, последние записи journal.md и файлы,
которые задача трогает.

**2. Проверить предпосылки.** До кода. Каждое утверждение о среде -
команда с выводом, вставленным в файл задачи. Версия nginx, наличие
роли в БД, поддержка возможности в PostgreSQL, что именно лежит на
сервере.

**3. Выписать крайние случаи.** До реализации, в файл задачи.

**4. Работать малыми шагами**, после каждого `make test` зелёный.

**5. Проверить наблюдаемый результат.** Не код ответа, а то, что видит
человек. Для страницы - открыть в браузере с консолью. Для API -
посмотреть на тело ответа. Для скрипта - проверить, что он сделал, а не
чем завершился.

**6. Закрыть задачу.** Пока не сделано, задача не закончена:

- файл задачи: статус, решения, факт в часах;
- `journal.md` - если что-то сломалось;
- `acceptance.md` - если появился новый сценарий;
- `openapi.yaml` - если менялся API, и `make api-lint` зелёный;
- ADR - если решение дорого отменять.

### Готово значит

- [ ] `make test` зелёный
- [ ] `make api-lint` зелёный, если API менялся
- [ ] Наблюдаемый результат проверен глазами
- [ ] Крайние случаи из файла задачи закрыты тестами
- [ ] Предпосылки в файле задачи подтверждены выводом команд
- [ ] Файл задачи дописан: решения, статус, факт
- [ ] `journal.md` дополнен, если было что записать
- [ ] Документация изменена тем же коммитом, что и код

Последний пункт не формальность. Отложенная документация не пишется
никогда, а документация, написанная через неделю по памяти, - это
класс D.

## 4. Чем закрыть каждый класс

Порядок - по отношению пользы к трудозатратам.

### 4.1. Браузерный сквозной тест (класс B)

Самое дорогое, что случилось в проекте, - белый экран при идеальных
логах. Ни один серверный тест его не видит: сервер отдаёт ровно то, что
просили.

Playwright ловит его целиком: браузер грузит страницу, подтягивает
скрипты, выполняет их и показывает результат. Минимальный сценарий,
который поймал бы **оба** немых отказа:

```
открыть /
нажать «Открыть демо»
дождаться дашборда
проверить: ноль ошибок в консоли
проверить: ноль запросов со статусом 4xx и 5xx
проверить: на странице есть строки позиций
```

Дальше - сценарий из ТЗ: открыть демо, промотать неделю, получить
напоминание, оформить заказ, принять, увидеть зелёную позицию. Он же
уже описан словами в [acceptance.md](acceptance.md), остаётся записать
кодом.

Запускается после выката против прода как часть проверки и в CI против
поднятого локально окружения.

Оценка: половина дня на каркас и смоук, ещё день на полный сценарий.

### 4.2. Сверка ответов с контрактом (класс D)

Три из пяти ошибок класса D - это расхождение OpenAPI с кодом. Они
исчезают, если каждый ответ HTTP-тестов проверяется против
`openapi.yaml`.

В ТЗ (14.1) для этого уже назван `kin-openapi`: схема загружается один
раз, в тестовом клиенте появляется обёртка, которая валидирует каждый
ответ. Тест перестаёт быть зелёным, если код разошёлся с документом, -
и документ перестаёт быть художественным произведением.

Оценка: половина дня.

### 4.3. Проверка предпосылок командой (класс A)

Дешевле всего и даёт больше всего. Ничего писать не нужно - нужна
привычка: **ни одного утверждения о среде без вывода команды рядом.**

Для повторяющихся проверок - цель `make doctor`, которая ходит на
целевую машину и печатает факты: версии nginx, PostgreSQL, Go, свободное
место, список сервисов, имя включённого конфига nginx. Запускается перед
любой работой с инфраструктурой.

Оценка: час.

### 4.4. Обязательные крайние случаи (класс E)

Не инструмент, а раздел шаблона задачи. Перед реализацией выписывается
список: пусто, ноль, один, вырожденное, предельное, чужая кодировка,
враждебный ввод. Каждый пункт - строка таблицы теста.

Таблица тестов кодировок CSV появилась именно так, уже после того как
CP1251 уронил импорт.

Оценка: ноль, это дисциплина.

### 4.5. Сквозные тесты на швы (класс C)

Уже есть и работают: три бага из четырёх в этом классе нашли они.
Дописывать по мере появления новых связок между модулями.

Отдельно стоит выписать в CONVENTIONS.md контракты, которые уже дорого
обошлись:

- «сейчас» для события бизнеса - всегда время тенанта, системные часы
  только для технических отметок;
- статус заказа меняется до создания движений, а не после;
- пересчёт статуса позиции - в той же транзакции, что и движение.

### 4.6. Правила в файлах (класс F)

`.gitattributes` уже добавлен. Дополнительно: все команды идут через
контейнер с зафиксированной версией, версии инструментов прибиты в CI и
в Makefile.

### Чего делать не стоит

**Поднимать здесь Prometheus с Grafana.** На машине с 961 МБ ОЗУ они
стоят дороже всего, за чем наблюдают. `/metrics` отдаётся, внешний сбор
подключается когда угодно.

**Гоняться за покрытием.** Ни один дефект проекта не был бы найден
лишними процентами покрытия. Их находили сквозные тесты, вырожденные
данные и открытый браузер.

**Писать юнит-тесты на HTTP-хендлеры.** Два бага в проводке маршрутов
поймали тесты, ходящие по HTTP целиком; юнит-тест хендлера не видит,
что хендлер зарегистрирован не в той группе.
