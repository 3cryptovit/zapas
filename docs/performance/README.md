# Производительность

Целевые числа заданы в §12 ТЗ. Здесь — как они проверяются и что
получилось при последнем прогоне.

| Требование | Цель | Замер |
|---|---|---|
| `GET /dashboard` | ≤ 300 мс (p95) | **22,7 мс** |
| `POST /movements` | ≤ 150 мс (p95) | **34,2 мс** |
| Создание песочницы | ≤ 3 с (p95) | **1,5 с** на проде |

Первые две строки — прогон k6 на локальной машине: 300 позиций,
1 000 500 движений, 10 одновременных пользователей, 70 секунд, 0 ошибок
на 27 935 запросов. Третья — замер на боевом сервере.

Нагружать прод нельзя: машина общая с пятью проектами, у одного из них
настоящие посетители. Поэтому цифры из k6 получены локально, а с прода
берутся только те метрики, которые он отдаёт сам.

## Как повторить

**Не запускайте это против прода.** Сервер общий с пятью другими
проектами, у одного из них настоящий домен и настоящие посетители.
Сценарий пишет движения и грузит машину — ему место на локальной базе.

```bash
docker compose -f deploy/docker-compose.yml up -d postgres redis

app migrate up
app seed -email perf@zapas.local -password 'perf-parol-42' -name 'Нагрузка'
psql -d zapas -v ON_ERROR_STOP=1 -f tests/load/fixture.sql   # около 2 минут

app api &
k6 run -e BASE_URL=http://localhost:8080 tests/load/api.js
```

Фикстура идемпотентна: повторный запуск видит уже наполненную
организацию и выходит.

## Почему дашборд быстрый

Главный запрос вообще не заглядывает в таблицу движений — а это
435 МБ из 440 МБ всей базы:

```
Sort (actual time=1.741..1.755 rows=300 loops=1)
  Buffers: shared hit=56
  -> Hash Left Join (actual time=0.846..1.281 rows=300)
     -> Seq Scan on stock_balances b (rows=300)
     -> Seq Scan on items i (rows=300)
     -> Seq Scan on item_status st (rows=300)
```

1,7 мс, 56 страниц из кэша, ни одного обращения к диску. Так вышло
потому, что остаток материализован в `stock_balances` и пересчитывается
той же транзакцией, что пишет движение. Журнал остаётся неизменяемой
историей, а экран читает готовое число.

Цена этого решения — обязанность держать остаток и журнал в согласии.
Поэтому ночная задача `reconcile` сверяет их и поднимает метрику
`zapas_balance_drift_total`, за которой следит сторож.

## Что происходит с миллионом движений

Лента движений идёт по индексу и не зависит от размера таблицы:

```
Limit (actual time=0.067..0.119 rows=50)
  -> Index Scan using stock_movements_tenant_occurred_idx
     Index Cond: (tenant_id = ...)
  Execution Time: 0.307 ms
```

Полная сверка одной позиции читает все её 3381 движение за 11 мс —
это и есть цена честной проверки «остаток равен сумме движений».
Выполняется она ночью, а не в запросе пользователя.

## Размеры

```
stock_movements   435 MB
daily_consumption 5448 kB
forecasts         688 kB
items             224 kB
```

Миллион движений — это примерно три года работы кофейни. 435 МБ на
трёхлетнюю историю означает, что на боевом сервере с 1,9 ГБ свободного
места одна организация поместится с запасом, а десяток — уже нет. Это
известное ограничение текущего размещения, а не архитектуры: база
переезжает на отдельный диск без изменений в коде.

## Чего здесь нет

Prometheus с Grafana, которые ТЗ упоминает рядом с k6. На машине с
961 МБ ОЗУ, поделённой между шестью проектами, они стоили бы дороже
всего, за чем наблюдают. Вместо них — `/metrics` в формате Prometheus
(к нему в любой момент можно подключить внешний сбор) и лёгкий сторож
`zapas-watchdog`, который проверяет то, что действительно ломается, и
пишет в Telegram. Подробности — в [runbooks/README.md](../runbooks/README.md).
