# Фича: движения и остатки

Закрывает FR-7 … FR-11, FR-16, FR-17 и §10.2.

## Контекст и цель

Владелец должен уметь объяснить любую цифру на складе. Значит, остаток нельзя
редактировать напрямую: он равен сумме неизменяемых движений. При этом дашборд
на 300 позиций обязан отвечать за 300 мс, а два бариста, списывающие одно
и то же молоко одновременно, не должны увести остаток в минус.

## Требования и крайние случаи

| # | Требование | Крайний случай |
|---|---|---|
| FR-7 | Движение нельзя изменить или удалить | Сторно возможно ровно один раз; сторно сторна запрещено |
| FR-8 | Расход сверх остатка отклоняется | В ответе 409 есть текущий остаток; неудачная попытка не оставляет следов |
| FR-9 | `occurred_at` не дальше 7 дней назад | Часы телефона спешат — запас 5 минут вперёд |
| FR-10 | Повтор с тем же ключом не создаёт второе движение | Два одинаковых запроса одновременно: второй проигрывает на уникальном индексе |
| FR-11 | Журнал с фильтрами и курсорной пагинацией | Вставка новых движений не должна ломать страницы |
| FR-16 | `on_hand`, `on_order`, позиция запаса | Позиция без движений — ноль, а не отсутствие строки |
| FR-17 | Остаток равен сумме движений | Ночная сверка ловит расхождение и шлёт его в Sentry |

Отдельно: списание требует причины, приход не может быть отрицательным,
архивная позиция движений не принимает.

## Решение

Порядок записи движения (§10.2), всё в одной транзакции:

1. Повтор по ключу идемпотентности → вернуть уже созданное движение.
2. `SELECT … FOR UPDATE` по строке остатка — конкурентные списания
   выстраиваются в очередь.
3. Проверка `on_hand + qty >= 0` → иначе 409 с текущим остатком.
4. `INSERT` движения.
5. `UPDATE` остатка.
6. Пересчёт `item_status`; при ухудшении — запись в `notifications` и `outbox`.

Знак ставит сервер по типу движения: наружу количество всегда передаётся
положительным. Права на `UPDATE` и `DELETE` для `stock_movements` отозваны
у роли приложения — «поправить вчерашнее списание» невозможно даже при баге
в коде.

Курсор пагинации — пара `(occurred_at, id)`, закодированная в base64url.
`OFFSET` не годится: при вставке новых движений страницы поедут.

## Изменения API и схемы

Схема: `migrations/20260919090200_stock.sql`.

```
POST   /api/v1/movements              Idempotency-Key обязателен
POST   /api/v1/movements/{id}/reverse
GET    /api/v1/movements              ?item_id=&type=&author_id=&from=&to=&cursor=&limit=
```

Ответ 201 сразу содержит новый остаток и статус, чтобы интерфейс обновился
без второго запроса. Ответ 409 несёт `on_hand` расширением RFC 9457.

Повтор с тем же ключом отдаёт **200**, а не 201: ничего нового не создано.

## План тестов

Интеграционные, на настоящем PostgreSQL (`internal/stock/integration_test.go`):

- `TestКонкурентность_ОстатокНеУходитВМинус` — 50 горутин, остатка хватает
  на 30: ровно 30 проходят, 20 получают 409, остаток 0 и равен журналу.
- `TestFR10_ИдемпотентностьПриГонке` — два одинаковых запроса одновременно.
- `TestFR7_Сторно` — повторное сторно и сторно сторна отклоняются.
- `TestFR8_ЗапретОтрицательногоОстатка` — ошибка несёт остаток, следов нет.
- `TestFR9_ВремяСобытия` — таблица из четырёх границ.
- `TestFR11_Журнал` — фильтры и сборка всех страниц без потерь и дублей.
- `TestИзоляция_ЧужойТенантНеВиденЧерезСервис`.

HTTP-уровень (`internal/api/http_test.go`): `TestСценарийСмены` проходит путь
приход → расход → попытка списать больше → сторно → журнал.

## Факт: 6 ч

Меньше оценки за счёт того, что схема со всеми ограничениями была готова
заранее: половина крайних случаев (знак по типу, причина списания,
неотрицательный остаток) проверяется самой БД, и в коде их проверять
не пришлось — только переводить ошибки ограничений в доменные.
