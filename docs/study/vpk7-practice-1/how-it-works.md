# Как Zapas устроен технически — простыми словами

Шпаргалка к защите: что из чего состоит, кто кому что отправляет и в
каком формате. Всё сверено с кодом и конфигами деплоя.

---

## 1. Вся система на одной картинке

```
                          Интернет
                              │  HTTPS (сертификат Let's Encrypt)
                              ▼
                     ┌─────────────────┐
  Браузер ──────────▶│      nginx      │◀────────── Telegram (вебхук)
  (React-приложение) │  «вахтёр» на    │
                     │  входе          │
                     └───┬─────────┬───┘
            /, /app/     │         │  /api/...
    отдаёт готовые файлы │         │  пересылает на 127.0.0.1:8080
    (HTML, JS, CSS)      ▼         ▼
                   статика    ┌──────────┐          ┌──────────┐
                              │   API    │          │  Воркер  │
                              │ app api  │          │app worker│
                              └────┬─────┘          └──┬───┬───┘
                                   │                   │   │
                    SQL            ▼        SQL        ▼   │ задачи по расписанию
                              ┌────────────────────────┐   ▼
                              │      PostgreSQL        │ ┌───────┐
                              │ данные + очередь outbox│ │ Redis │
                              └────────────────────────┘ └───────┘
                                                   │
                                  воркер отправляет│
                                   ┌───────────────┴──────────┐
                                   ▼                          ▼
                          Telegram Bot API              SMTP-сервер
                          (HTTPS + JSON)                (почта)
```

Главное:

- **Программа одна** — бинарник `app`, написанный на Go. Он запускается в
  разных режимах: `app api` обслуживает запросы, `app worker` выполняет
  фоновые задачи, `app migrate` обновляет структуру базы, `app seed`
  создаёт тестовые данные для разработки. Такой подход называется
  «модульный монолит».
- **API и воркер не общаются друг с другом напрямую.** Общая у них только
  база: API кладёт в неё задание «отправить уведомление», воркер его
  забирает.

## 2. Кто есть кто

| Компонент | Что это простыми словами | Что делает |
|---|---|---|
| **Браузер** | React-приложение (TypeScript), скачивается один раз | рисует экраны, ходит в API за данными |
| **nginx** | «вахтёр» на входе сервера | держит HTTPS, отдаёт готовые файлы сайта, пересылает `/api/...` в API |
| **API** (`app api`) | Go-сервер на порту 8080, роутер chi | принимает запросы, проверяет права, считает, пишет в базу, отвечает JSON |
| **Воркер** (`app worker`) | тот же Go-бинарник в фоновом режиме | по расписанию пересчитывает прогнозы, собирает сводки, рассылает уведомления, чистит старые демо |
| **PostgreSQL 16** | основная база данных | хранит всё: склад, заказы, прогнозы, сессии, очередь уведомлений |
| **Redis** | быстрое хранилище в памяти | расписание и очередь задач воркера (библиотека asynq); счётчик лимита демо для API |
| **Telegram Bot API** | внешний сервис | доставляет сообщения владельцу и присылает нам то, что пишут боту |
| **SMTP-сервер** | внешний почтовый сервер | доставляет письма |
| **Сторож** (watchdog) | bash-скрипт, запуск раз в 5 минут | проверяет, что всё живо, и пишет в Telegram, если что-то сломалось |
| **Бэкап** | bash-скрипт, каждый день в 04:00 | сохраняет копию базы |

## 3. Путь одного запроса: сотрудник списал молоко

Так проходит одно нажатие кнопки «Списать».

1. **Браузер** отправляет запрос:
   ```http
   POST /api/v1/movements
   Cookie: zapas_session=…; zapas_csrf=…
   X-CSRF-Token: …
   Idempotency-Key: 7f3c…
   Content-Type: application/json

   {"type": "writeoff", "item_id": "…", "qty": "2.000", "reason": "spoiled"}
   ```
2. **nginx** видит путь `/api/`, расшифровывает HTTPS и пересылает запрос
   в API на `127.0.0.1:8080`. Снаружи порт 8080 недоступен.
3. **API, обязательная обработка.** Через неё проходит каждый запрос:
   - запросу присваивается номер для поиска в логах;
   - он пишется в лог и в метрики;
   - на ответ даётся не больше 30 секунд.
4. **API, проверка доступа:**
   - по cookie `zapas_session` находится сессия в базе, а по ней —
     пользователь и его кофейня;
   - заголовок `X-CSRF-Token` сравнивается с сессией, чтобы чужой сайт
     не мог отправить запрос от имени пользователя.
5. **API, три слоя кода:**
   `handler` (разбирает JSON) → `service` (бизнес-правила) →
   `repository` (SQL-запросы, сгенерированные утилитой sqlc).
6. **PostgreSQL, одна транзакция.** Шаги ниже выполняются как единое
   целое: либо все, либо ни одного.
   - Запомнить кофейню — дальше база сама не отдаст чужие строки (RLS).
   - Проверить `Idempotency-Key`. Если такой запрос уже был, вернуть
     прежний результат и не записывать дубль.
   - Заблокировать строку остатка молока. Если в ту же секунду списывают
     двое, они встанут в очередь.
   - Проверить, хватает ли остатка. Если нет — отменить транзакцию и
     ответить `409` с фактическим остатком.
   - Записать движение в журнал (записи из него никогда не удаляются) и
     обновить остаток.
   - Пересчитать статус позиции. Если молоко стало критичным, записать
     уведомление в ленту и в очередь `outbox`.
   - Подтвердить транзакцию.
7. **Ответ** `201 Created` с JSON-телом. Браузер обновляет экран.

Telegram в этой цепочке не участвует. Сообщение пока только лежит в
очереди, и его отправит воркер.

## 4. Воркер

Воркер — это отдельный процесс для работы, которую не нужно делать
«прямо сейчас, пока пользователь ждёт ответа».

**Как устроено расписание** (библиотека asynq поверх Redis):

- **планировщик** внутри воркера по часам кладёт задачи в Redis, как
  будильник;
- **исполнитель** забирает их из Redis и выполняет, до 4 задач
  одновременно.

| Задача | Как часто | Что делает |
|---|---|---|
| `notify:outbox` | каждые 30 секунд | берёт уведомления из очереди в базе и отправляет в Telegram или на почту |
| `forecast:nightly` | каждый час | у кофеен, где сейчас 03:00, пересчитывает прогноз и статусы |
| `notify:digest` | каждый час | собирает утреннюю сводку тем, у кого наступило её время (по умолчанию 09:00) |
| `notify:cutoff` | каждые 15 минут | напоминает, если до отсечки поставщика 2 часа, а заказ не отправлен |
| `notify:late` | каждый час | предупреждает, что поставка опаздывает |
| `stock:reconcile` | ночью | сверяет остатки с журналом движений |
| `sandbox:cleanup` | каждый час | удаляет демо старше 24 часов |

**Почему задачи запускаются «каждый час», а не «в 03:00»?** Кофейни могут
быть в разных часовых поясах: у одной 03:00 наступает раньше, у другой
позже. Поэтому задача просыпается каждый час и сама выбирает, у кого
сейчас нужное время.

**Что будет, если воркер упадёт?** Сайт продолжит работать: API от
воркера не зависит. Уведомления будут копиться в очереди `outbox` и
уйдут, когда воркер поднимется. systemd перезапускает его сам через
10 секунд.

## 5. Как уходит сообщение в Telegram

**Исходящее: мы → Telegram.**

1. Воркер раз в 30 секунд забирает пачку записей из `outbox` запросом
   `FOR UPDATE SKIP LOCKED`. Так два воркера не возьмут одно и то же
   сообщение.
2. Отправляет:
   ```http
   POST https://api.telegram.org/bot<токен>/sendMessage
   Content-Type: application/json

   {"chat_id": "123456", "text": "Заказать сегодня у Молочной фермы до 16:00: …"}
   ```
3. Смотрит на ответ:

   | Ответ | Что делаем |
   |---|---|
   | `200` | помечаем «отправлено» |
   | `400` / `403` (чата нет, бот заблокирован) | больше не пытаемся |
   | `429` (слишком часто), сеть, таймаут 10 с | повторяем через 1, 5, 25 минут, до 5 попыток |

**Входящее: Telegram → мы (вебхук).** Нужно, чтобы привязать чат.

1. Владелец открывает ссылку `t.me/<бот>?start=<код>` и пишет боту.
2. Telegram сам отправляет нам `POST` с JSON-сообщением на
   `/api/v1/telegram/webhook` (через nginx).
3. API проверяет заголовок `X-Telegram-Bot-Api-Secret-Token`. Без
   правильного секрета отвечает `403`.
4. Находит код, запоминает `chat_id` и отвечает в чат «Готово!».
5. Если секрет верный, Telegram получает `200`, даже когда мы не смогли
   обработать сообщение. Иначе он будет присылать его снова и снова.

**Почта.** Воркер отправляет письмо по протоколу SMTP; если сервер
молчит 20 секунд, отправка прерывается. При разработке письма ловит
локальный Mailpit, поэтому в настоящие ящики они не уходят.

## 6. Форматы: кто с кем и на каком языке говорит

| Кто → кому | Протокол | Формат |
|---|---|---|
| Браузер → nginx | HTTPS | JSON в кодировке UTF-8 |
| nginx → API | HTTP внутри сервера (127.0.0.1:8080) | тот же запрос без изменений |
| API → браузер, успех | HTTP | JSON |
| API → браузер, ошибка | HTTP | `application/problem+json` (стандарт RFC 9457): `{"title": "Недостаточно остатка", "status": 409, "detail": "…"}` |
| Импорт позиций | HTTP | файл `text/csv`, до 5 МБ |
| API и воркер → PostgreSQL | протокол PostgreSQL (драйвер pgx) | SQL-запросы с параметрами, без ORM |
| Воркер ↔ Redis | протокол Redis | задачи asynq |
| Воркер → Telegram | HTTPS | JSON |
| Telegram → API (вебхук) | HTTPS | JSON + секретный заголовок |
| Воркер → почта | SMTP | письмо в формате MIME |
| Логи | в журнал systemd | JSON, одна строка на событие |
| Метрики | HTTP, порт 9090, закрыт снаружи | текстовый формат Prometheus |
| Бэкап | файл | SQL-дамп (`pg_dump`), сжатый gzip |

**Договорённости внутри JSON:**

- **Количества — строками:** `"48.000"`, а не `48.0`. JavaScript хранит
  дроби неточно, а для литров и денег это недопустимо. В базе для них
  тип `numeric(14,3)` — ровно три знака после запятой.
- **Даты** — `"2026-09-23"`, время — ISO 8601 с поясом:
  `"2026-09-23T16:00:00+03:00"`.
- **Идентификаторы** — UUID: `"01a0ccb0-0723-75d9-…"`.
- **Cookies:**
  - `zapas_session` — ключ сессии, JavaScript его прочитать не может
    (httpOnly), поэтому украсть его скриптом нельзя;
  - `zapas_csrf` — JavaScript его читает и дублирует в заголовок
    `X-CSRF-Token`.

## 7. Сервер

Сервер — общий VPS, на котором кроме Zapas работают ещё пять проектов:
**1 процессор и 961 МБ памяти на всех**. Отсюда почти все решения.

| Что | Как сделано | Почему |
|---|---|---|
| Запуск | systemd-сервисы `zapas-api` и `zapas-worker`, без Docker | на Docker не хватит памяти |
| Ограничения | API — до 220 МБ памяти и 60% CPU, воркер — до 260 МБ и 70% CPU | чтобы Zapas не задушил соседние проекты |
| Автоперезапуск | `Restart=always`: API поднимается через 5 с, воркер через 10 с | упал — встал сам |
| HTTPS | Let's Encrypt на адрес `zapas.85.198.64.102.nip.io` | своего домена нет, а без HTTPS Telegram не пустит вебхук |
| База | отдельная база `zapas` в уже работающем PostgreSQL, три роли с разными правами | чужие базы не затронуты |
| Бэкап | каждый день в 04:00, хранятся 7 дневных и 4 недельных копии | чтобы можно было откатить данные |
| Наблюдение | сторож раз в 5 минут проверяет сервисы, `/readyz`, диск, память, очередь уведомлений, сертификат, свежесть бэкапа | о поломке пишет в Telegram, и только при переходе «работает ↔ сломалось» |

**Как выкатывается новая версия:**

1. Новый бинарник загружается рядом со старым.
2. Накатываются миграции базы. Если миграция упала, всё остаётся на
   старой версии.
3. Старый бинарник сохраняется как `app.prev`, новый встаёт на его место.
4. Откат — вернуть `app.prev`.

## 8. Вопросы по архитектуре и короткие ответы

**Почему монолит, а не микросервисы?**
Проект маленький, и памяти на сервере мало. Одна программа проще в
разработке и деплое. Внутри она всё равно разделена на модули: склад,
прогноз, заказы, уведомления.

**Зачем отдельный воркер, если есть API?**
Чтобы пользователь не ждал. Отправка в Telegram может занять секунды или
вовсе не пройти, а пересчёт прогноза по всем позициям — тяжёлая работа.
API отвечает сразу, а медленное делает воркер в фоне.

**Что такое outbox и зачем он?**
Очередь исходящих сообщений в своей же базе. Уведомление записывается в
той же транзакции, что и событие, поэтому не бывает, что списание
сохранилось, а уведомление потерялось. Даже если Telegram недоступен,
сообщение дождётся отправки.

**Зачем Redis, если есть PostgreSQL?**
Для двух вещей, где он удобнее: расписание фоновых задач (asynq) и
счётчик «не больше 5 демо в час с одного IP». Все данные бизнеса живут
только в PostgreSQL.

**Как не перепутать данные разных кофеен?**
Кофейня определяется только по сессии и никогда — по адресу или телу
запроса. В базе включена построчная защита (RLS): даже если в коде
ошибка, база не отдаст чужие строки. Чужой объект возвращает 404, а не
403, чтобы нельзя было узнать, что он существует.

**Что будет, если два человека одновременно спишут последний литр?**
Строка остатка блокируется, и второй запрос ждёт первого. Первый
спишет, второй увидит, что остатка не хватает, и получит 409. Это
проверено тестом, в котором 50 параллельных запросов списывают одну
позицию.

**Как работает «промотка времени» в демо?**
Код нигде не берёт системное время напрямую, только через свой объект
`Clock`. У демо-кофейни часы сдвинуты вперёд, а после сдвига API сразу
пересчитывает прогноз.

**Как это масштабировать?**
Воркеров можно запустить несколько: `SKIP LOCKED` не даст им взять одно
и то же сообщение. API не хранит состояние в памяти, поэтому его тоже
можно запустить в нескольких копиях за nginx.
