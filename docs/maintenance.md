## 1. Сегодня (один раз)

Система уже работает на https://zapas.85.198.64.102.nip.io. Не хватает
того, что делается руками владельца.

### 1.1. Положить код в git

Подробный порядок со скриншотными шагами, настройкой секретов, защитой
ветки и разбором красной сборки — в [github-setup.md](github-setup.md).
Здесь только суть.

Репозиторий инициализирован, ветка `main`, коммитов нет.

```bash
cd D:\pet_proect

git config user.name "Ваше Имя"
git config user.email "vitalnessss@gmail.com"
```

Почта должна совпадать с привязанной к GitHub — иначе коммит не
свяжется с профилем и не попадёт в календарь активности.

Проверьте, что лишнее не уедет:

```bash
git status
git check-ignore -v .env bin/app-linux web/node_modules
```

Вторая команда должна подтвердить, что эти пути игнорируются.
Секретов в коде нет — проверено `gitleaks`, находок ноль.

```bash
git add -A
git commit -m "Zapas: учёт остатков и прогноз закупок для кофеен"
git remote add origin https://github.com/3cryptovit/zapas.git
git push -u origin main
```

Вместо пароля GitHub потребует personal access token: Settings →
Developer settings → Personal access tokens → Tokens (classic), права
`repo`. Либо поставьте [GitHub CLI](https://cli.github.com/) и один раз
выполните `gh auth login`.

### 1.2. Проверить, что CI позеленел

После push откройте вкладку **Actions**. Пайплайн запускается сам и
делает восемь проверок: формат кода, `go vet`, `golangci-lint`, тесты
под детектором гонок, сверку сгенерированного `sqlc`, поиск секретов,
проверку уязвимостей, фронтенд (линт, типы, тесты, сборка), линт
контракта API и сборку бинарника.

Если что-то красное — смотрите лог именно этого шага, там написано что.
Чаще всего это формат: `make fmt` и повторный коммит.

### 1.3. Дать GitHub доступ к серверу

Нужно, только если хотите выкатывать кнопкой из браузера. С машины
разработчика выкат работает и без этого.

Settings → Secrets and variables → Actions → New repository secret:

| Имя | Значение |
|---|---|
| `PROD_SSH_KEY` | содержимое `~/.ssh/zapas` целиком, вместе со строками BEGIN и END |
| `PROD_HOST` | `85.198.64.102` |
| `PROD_USER` | `root` |

```bash
cat ~/.ssh/zapas
```

Ключ уже прописан на сервере в `/root/.ssh/authorized_keys` под именем
`zapas-deploy`, вход по нему проверен.

### 1.4. Сменить засвеченные секреты

Пароль root и токен Telegram-бота передавались в переписке. Оба рабочие.

**Ключи вместо пароля.** Порядок важен: сначала убедиться, что ключ
пускает, и только потом закрывать пароль.

```bash
ssh -i ~/.ssh/zapas root@85.198.64.102     # проверяем, что входит
nano /etc/ssh/sshd_config                  # PasswordAuthentication no
systemctl reload ssh
```

Отдельно поменяйте сам пароль — `passwd` — на случай, если вход по
паролю когда-нибудь вернут.

**Токен бота.** В [@BotFather](https://t.me/BotFather): `/mybots` →
`@zapas_tg_bot` → API Token → Revoke current token. Новый — на сервер:

```bash
nano /etc/zapas/zapas.env        # TELEGRAM_BOT_TOKEN=новый
systemctl restart zapas-api zapas-worker
```

После смены токена вебхук надо поставить заново:

```bash
set -a; . /etc/zapas/zapas.env; set +a
curl -s "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/setWebhook" \
  -d "url=https://zapas.85.198.64.102.nip.io/telegram/webhook" \
  -d "secret_token=$TELEGRAM_WEBHOOK_SECRET"
```

Пароли базы менять не нужно: они созданы на сервере, лежат в
`/etc/zapas/db.secrets` и в переписке не появлялись.

### 1.5. Включить оповещения себе в Telegram

Сторож проверяет прод каждые 5 минут, но пока пишет только в журнал
systemd. Чтобы получать сообщения:

1. Узнайте свой chat_id у [@userinfobot](https://t.me/userinfobot).
2. На сервере добавьте строку в `/etc/zapas/zapas.env`:
   `ZAPAS_ALERT_CHAT_ID=<ваш id>`
3. Проверьте: `/srv/zapas/bin/watchdog.sh`

Сообщение приходит только на переходе «работает → сломалось» и
обратно. Если авария затянулась — напоминание раз в 6 часов. Так
сделано намеренно: сообщение каждые пять минут перестают читать.

### 1.6. Лицензия

Файла `LICENSE` нет — это решение о правах на ваш код, и в нём должно
стоять ваше имя. Для портфолио обычно берут MIT.

GitHub умеет создать сам: Add file → Create new file → имя `LICENSE` →
справа появится «Choose a license template».

После этого допишите в `docs/api/openapi.yaml`, в блок `info`:

```yaml
  license:
    name: MIT
    url: https://github.com/3cryptovit/zapas/blob/main/LICENSE
```

Это последнее предупреждение линтера OpenAPI.

## 2. Выкат

### Обычный релиз

```bash
ZAPAS_SSH_KEY=~/.ssh/zapas scripts/deploy.sh
```

Собирает linux-бинарник в контейнере, собирает кабинет и лендинг,
заливает, накатывает миграции, перезапускает сервисы, проверяет
`/healthz` и `/readyz`. Занимает пару минут, простоя нет.

Из браузера то же самое: **Actions → Deploy → Run workflow**, в поле
подтверждения написать `deploy`. Сделано вручную намеренно: сервер
общий с пятью другими проектами, и решение «выкатываем сейчас»
принимает человек, а не push в ветку.

### Что происходит внутри и почему в таком порядке

1. Новый бинарник ложится рядом как `app.new` — работающий не тронут.
2. Накатываются миграции. **Упали — выкат останавливается здесь**, прод
   продолжает работать на прежней версии и ничего не замечает.
3. Текущий `app` копируется в `app.prev` — это запас для отката.
4. `app.new` занимает место `app`.
5. `systemctl restart zapas-api zapas-worker`.
6. Проверяются `/healthz` и `/readyz`.

### Главное правило про миграции

**Миграция должна работать и со старой версией кода.** Между шагом 2 и
шагом 5 старый код уже видит новую схему.

Отсюда практика: колонку сначала добавляют (релиз N), код начинает её
писать и читать (релиз N), и только релизом N+1 перестают писать в
старую и удаляют её. Три релиза вместо одного, зато ни один из них не
роняет прод.

Нельзя: переименовать колонку одной миграцией, удалить колонку, на
которую ещё ссылается работающий код, добавить `NOT NULL` без значения
по умолчанию.

### Конфиг nginx выкатывается отдельно

`deploy.sh` его не трогает: конфиг общий с чужими проектами, и менять
его должен человек. Порядок с проверкой и откатом — в
[runbooks/deploy.md](runbooks/deploy.md).

Две ловушки, на которые уже наступали: на сервере файл называется
`sites-available/zapas` (**без** `.conf`, в отличие от репозитория), и
`nginx -t` перед `reload` обязателен — битый конфиг положит не только
Zapas.

Никогда `systemctl restart nginx`, только `reload`.

**Про `alias` в nginx.** Если добавляете локацию с `alias`, делайте её
префиксной (`location /app/assets/`), а не регулярной
(`location ~* ^/app/assets/`). В регулярной локации `alias`
подставляется целиком, остаток пути не дописывается, и все файлы
схлопываются в один каталог: `301`, затем `403`, и белый экран при
идеальных логах.

### Откат

Если миграций в релизе не было:

```bash
cp -p /srv/zapas/bin/app.prev /srv/zapas/bin/app
systemctl restart zapas-api zapas-worker
```

Десять секунд. Если миграции были — сначала всё равно попробуйте так:
они пишутся совместимыми, и старый код обычно работает с новой схемой.

`migrate down` в проде запрещён намеренно: `down`-миграции почти
никогда не проверяются на реальных данных, и непроверенный `DROP` в
разгар аварии превращает сбой в потерю данных. Вместо него —
исправляющая миграция или восстановление из бэкапа
([rollback.md](runbooks/rollback.md)).

### Проверка после выката

```bash
curl -s https://zapas.85.198.64.102.nip.io/readyz
journalctl -u zapas-api -n 30 --no-pager | grep -i error
```

Проверка после выката теперь не ограничивается `/healthz`: она берёт
настоящий HTML кабинета, вытаскивает из него ссылки на скрипты и стили
и дёргает каждую.

```
==> smoke
  /healthz: 200
  /readyz: 200
  /app/: 200
  /: 200
  assets:
    /app/assets/index-D3fAJceI.js: 200
    /app/assets/index-uiplkM0W.css: 200
```

Это добавлено после того, как кабинет месяц отдавал `200` на страницу
и `403` на все её скрипты — то есть был белым экраном, о котором
`/healthz` ничего не знал.

И всё равно откройте кабинет глазами. Машина проверяет коды ответов,
человек видит страницу; между этими двумя вещами уже дважды
обнаруживалась разница.

## 3. Новая функциональность

### Порядок работы

1. **Описать фичу** в `docs/features/<имя>.md` по шаблону: контекст и
   цель → требования и крайние случаи → изменения API и схемы → план
   тестов → оценка в часах → факт в часах.
2. **Небольшими шагами**, после каждого `make test` зелёный.
3. **Тест на каждое требование.** Номер FR указывается в имени теста —
   так видно, что закрыто, а что нет.
4. **Запись в `docs/journal.md`**, если случай того стоит.

Поле «Факт» заполняется всегда, даже когда расхождение с оценкой
неприятное: сравнение оценки и факта — это то же, что команды меряют
в KPI.

### Девять запретов

Они в [CONVENTIONS.md](../CONVENTIONS.md) и проверяются линтером и ревью:

1. Без ORM — только `sqlc` и параметризованные запросы.
2. Без `time.Now()` вне `internal/clock` и `main` — время из `clock.Clock`.
3. Без `float64` для количеств и денег — только `decimal` и `numeric(14,3)`.
4. Без правки применённых миграций — ошибку исправляет новая.
5. Без `tenant_id` из тела запроса или URL — только из сессии.
6. Без изменения `stock_movements` — таблица append-only, исправление через `reversal`.
7. Без бизнес-логики в HTTP-хендлерах — handler → service → repository.
8. Без прямых запросов в таблицы чужого модуля.
9. Без `COPY FROM` — PostgreSQL не поддерживает его для таблиц с RLS.

Каждый запрет стоит там не из вкуса: причины в `docs/adr/`.

### Новая миграция

Имя — метка времени и смысл, строго по возрастанию:

```
migrations/20260921120000_add_item_barcode.sql
```

Внутри — секции goose `-- +goose Up` и `-- +goose Down`. `Down` пишется
для локальной разработки; в проде он не выполняется (см. выше).

```bash
make migrate         # накатить локально
make migrate-status  # посмотреть, что применено
```

Новая таблица с данными организации **обязана** получить политику RLS —
иначе данные одной кофейни станут видны другой. Смотрите, как это
сделано в `migrations/20260919090600_rls.sql`, и повторите для своей
таблицы. Это самая дорогая ошибка из возможных здесь.

### Новый запрос

SQL живёт в `queries/*.sql`, код генерируется:

```bash
make sqlc
```

Сгенерированное в `internal/platform/sqlc/` руками не правят. В CI
стоит `sqlc diff`: если сгенерированный код отстал от запросов, сборка
краснеет.

### Изменение API

Контракт — `docs/api/openapi.yaml`, он не генерируется из кода, а
поддерживается руками. Добавили или изменили ручку — поправьте и его:

```bash
make api-lint
```

Плюс типы фронтенда в `web/src/lib/types.ts` — они тоже пишутся руками.

### Тесты

```bash
make test        # всё под детектором гонок
make cover       # покрытие пакетов ядра
```

Пакеты `forecast` и `replenishment` — чистые функции, закрыты
табличными тестами. Склад и API проверяются на настоящем PostgreSQL,
включая конкурентность, идемпотентность и изоляцию организаций.

Нагрузочный прогон — отдельно и **только локально**:

```bash
make perf-fixture   # 300 позиций, 1 млн движений, около 2 минут
make perf
```

Против прода его гонять нельзя: машина общая, у соседнего проекта
настоящие посетители.

## 4. Регулярная поддержка

Основную работу делают таймеры. Ваше участие сводится к нескольким
проверкам и редким обновлениям.

### Что работает само

| Что | Когда | Кто |
|---|---|---|
| Бэкап базы | 04:00 ежедневно | `zapas-backup.timer` |
| Проверка прода | каждые 5 минут | `zapas-watchdog.timer` |
| Продление сертификата | дважды в сутки, обновит за 30 дней до конца | `certbot.timer` |
| Пересчёт прогноза | каждый час | воркер |
| Сверка остатков с журналом | ночью | воркер |
| Удаление истёкших демо | каждый час | воркер |

Текущий сертификат действует до **18 декабря 2026**. Certbot обновит
сам; сторож предупредит, если за 10 дней до конца этого не произойдёт.

### Раз в неделю: пять минут

```bash
ssh root@85.198.64.102 '
  /srv/zapas/bin/watchdog.sh
  ls -la /var/backups/zapas/daily/ | tail -3
  df -h /
  free -m
'
```

Смотрите на три вещи: сторож вернул код 0, за вчера есть свежий дамп
осмысленного размера (около 150 КБ на нынешних данных, не нули),
свободного места больше гигабайта.

Свободная память гуляет в пределах 350–500 МБ — это нормально, соседние
проекты тоже работают. Тревожит не низкое число само по себе, а когда
сторож скажет, что осталось меньше 60 МБ.

### Раз в месяц: полчаса

**Учебное восстановление.** Бэкап, который ни разу не восстанавливали,
бэкапом не считается. Порядок в [restore.md](runbooks/restore.md), он
безопасен и боевую базу не трогает. Занимает пять минут.

**Обновления системы.** Машина общая, поэтому осторожно:

```bash
apt update
apt list --upgradable
apt upgrade                  # смотрите, что именно обновляется
```

Если в списке `nginx` или `postgresql` — обновляйте отдельно и сразу
проверяйте все шесть проектов на машине. Ядро обновляйте, когда готовы
перезагрузить сервер.

**Зависимости проекта.**

```bash
go get -u ./... && go mod tidy && make test
cd web && npm outdated
```

Обновляйте по одной библиотеке, а не всё сразу: так понятно, что
сломалось.

### Раз в квартал

- Прогнать `make perf` локально и сравнить с
  [docs/performance/](performance/README.md). Если дашборд стал вдвое
  медленнее — разбираться сейчас, а не когда упрётесь.
- Перечитать `docs/journal.md`. Это не формальность: записи там
  устроены как «что сломалось и почему», и половина будущих ошибок уже
  описана.
- Посмотреть размер базы. `pg_size_pretty(pg_database_size('zapas'))`.

### Чего делать не нужно

Ходить на сервер без причины. Сторож проверяет чаще и внимательнее, а
каждая ручная правка в обход репозитория — это расхождение между тем,
что в git, и тем, что работает.

## 5. Когда сломалось

### Первые три команды

```bash
ssh root@85.198.64.102
/srv/zapas/bin/watchdog.sh                 # что именно не так
systemctl status zapas-api zapas-worker
journalctl -u zapas-api -n 50 --no-pager
```

Сторож перечислит проблемы словами. Дальше — по таблице.

| Симптом | Куда смотреть |
|---|---|
| Сайт не открывается вообще | `systemctl status nginx`, `nginx -t` |
| Открывается, но 502 | `systemctl status zapas-api`, журнал сервиса |
| `/readyz` отдаёт 503 | недоступны PostgreSQL или Redis, смотрите `checks` в ответе |
| Уведомления не приходят | `zapas-worker`, очередь: метрика `zapas_outbox_pending` |
| Telegram молчит | токен в `/etc/zapas/zapas.env`, вебхук через `getWebhookInfo` |
| Остатки не сходятся | метрика `zapas_balance_drift_total`, ночная задача `reconcile` |
| Демо не открывается | [sandbox-abuse.md](runbooks/sandbox-abuse.md) |
| Стало хуже после выката | [rollback.md](runbooks/rollback.md) |
| Данные испорчены | [restore.md](runbooks/restore.md) |

### Немой отказ

Самый неприятный случай: кодов ошибок нет, в журнале `200`, метрики
прекрасные — а пользователь говорит «не работает». Такое уже случалось
дважды подряд:

- сервер отдавал адрес без слеша на конце, браузер честно переходил и
  показывал лендинг вместо кабинета;
- кабинет отдавал `200` на страницу и `403` на все её скрипты, то есть
  был белым экраном.

В обоих случаях в журнале nginx стояли аккуратные `200`, а сторож
молчал — потому что с его точки зрения всё работало.

Разбор такого начинается не с логов, а с браузера: откройте консоль
разработчика (F12), вкладку Network, и посмотрите, что именно красное.
Логи сервера покажут запрос, но не покажут, что страница с ним сделала.

Проверить то же из терминала:

```bash
B=https://zapas.85.198.64.102.nip.io
curl -s "$B/app/" | grep -oE '(src|href)="/app/assets/[^"]+"' | cut -d'"' -f2 |
  while read a; do echo "$a $(curl -s -o /dev/null -w '%{http_code}' "$B$a")"; done
```

Все строки должны заканчиваться на `200`.

### Сохранить улики

Журнал systemd не бесконечен. Прежде чем чинить:

```bash
journalctl -u zapas-api --since '30 min ago' --no-pager > /tmp/incident.log
```

И запишите произошедшее в `docs/journal.md`. Следующий такой случай
начнётся с чтения этой записи.

## 6. Пределы этой установки

Сервер общий: 1 vCPU, 961 МБ ОЗУ, около 1,9 ГБ свободного диска, и на
нём работают ещё пять проектов, у одного из которых настоящий домен и
настоящие посетители. Это определило почти все решения по размещению и
задаёт границы.

| Ресурс | Сейчас | Когда станет тесно |
|---|---|---|
| База | 12 МБ | миллион движений — это 435 МБ, то есть около трёх лет одной кофейни |
| Память | занято 450–620 из 961 МБ, плавает | лимиты в юнитах: API 220 МБ, воркер 260 МБ |
| Диск | занято около 80% | бэкапы лежат на том же диске, что и база |
| Демо | до 60 одновременно | сверх — лендинг показывает видео вместо кнопки |

### Что делать первым, когда упрётесь

1. **Бэкапы за пределы сервера.** Сейчас дампы лежат на том же диске,
   что и база: потеря диска — потеря и того, и другого. Это самое
   слабое место текущей схемы, и чинится оно проще всего.
2. **Отдельный диск под базу.** Переезд не требует изменений в коде.
3. **Свой сервер под Zapas.** Тогда же имеет смысл вернуть Docker
   Compose, внешний мониторинг и всё, от чего пришлось отказаться.
4. **Домен вместо nip.io.** Нужен, как только появится настоящий
   клиент: адрес с IP внутри доверия не вызывает.

### Чего делать не нужно

Поднимать здесь Prometheus с Grafana. На машине с 961 МБ ОЗУ они
стоили бы дороже всего, за чем наблюдают. `/metrics` в формате
Prometheus уже отдаётся на закрытом порту — внешний сбор подключается
в любой момент без единой правки в коде.
