# Заводим GitHub и CI/CD

Разовая настройка: от пустого репозитория до зелёного пайплайна и
кнопки выката. Делается один раз, дальше — [maintenance.md](maintenance.md).

---

## Что уже готово

| | |
|---|---|
| `.github/workflows/ci.yml` | Восемь проверок, запускается сам на push и на pull request |
| `.github/workflows/deploy.yml` | Выкат на прод, только вручную |
| `.gitignore` | `.env`, `bin/`, `node_modules`, `dist` — не уедут |
| `.gitattributes` | Переводы строк зафиксированы, иначе Windows ломает проверку формата |
| `.golangci.yml` | Версия линтера прибита и совпадает с CI |

Все восемь проверок прогнаны локально и зелёные. Значит первый push не
должен покраснеть — а если покраснеет, смотрите [таблицу
отказов](#если-сборка-красная).

---

## Шаг 1. Представиться git

Имя и почта попадут в каждый коммит как авторство.

```bash
cd D:\pet_proect

git config user.name "Ваше Имя"
git config user.email "vitalnessss@gmail.com"
```

Почта обязана совпадать с привязанной к GitHub. Иначе коммиты не
свяжутся с профилем и не попадут в календарь активности — для портфолио
это половина смысла.

Проверить, что привязано: GitHub → Settings → Emails.

## Шаг 2. Посмотреть, что уедет

```bash
git status
git check-ignore -v .env bin/app-linux web/node_modules
```

Вторая команда должна напечатать три строки — значит эти пути
игнорируются. Если она молчит, `.gitignore` не подхватился.

Секретов в коде нет: `gitleaks` прогнан, находок ноль. Боевые пароли
лежат на сервере в `/etc/zapas`, в репозиторий они никогда не попадали.

## Шаг 3. Первый коммит

```bash
git add -A
git status --short | head -20
git commit -m "Zapas: учёт остатков и прогноз закупок для кофеен"
```

Перед `commit` стоит пробежать глазами список: это единственный момент,
когда лишний файл легко убрать.

## Шаг 4. Создать репозиторий на GitHub

Через сайт: **New repository** → имя `zapas` → **Public** → и ничего не
добавлять (ни README, ни .gitignore, ни лицензию — они уже есть, иначе
получите конфликт при первом push).

Либо через [GitHub CLI](https://cli.github.com/), тогда шаги 4 и 5
сливаются в один:

```bash
gh auth login
gh repo create zapas --public --source=. --remote=origin --push
```

## Шаг 5. Отправить код

```bash
git remote add origin https://github.com/3cryptovit/zapas.git
git branch -M main
git push -u origin main
```

Вместо пароля GitHub попросит **personal access token**: Settings →
Developer settings → Personal access tokens → Tokens (classic) →
Generate new token, отметить права `repo`. Обычный пароль от аккаунта
не подойдёт.

Токен вводится один раз, дальше его запомнит менеджер учётных данных
Windows.

## Шаг 6. Посмотреть, как идёт сборка

Сразу после push откройте вкладку **Actions**. Пайплайн запустится сам.
Восемь работ, они идут параллельно, целиком — минуты три-четыре.

| Работа | Что проверяет | Почему это здесь |
|---|---|---|
| **Go — статический анализ** | `gofmt`, `go vet`, `golangci-lint` | Незаформатированный код не мёржится; линтер ловит незакрытые тела ответов, необработанные ошибки, подделываемые заголовки |
| **Go — тесты** | Весь набор под детектором гонок, на настоящем PostgreSQL и Redis | Изоляция организаций, конкурентность, идемпотентность — всё это проверяется только на живой базе |
| **sqlc** | `sqlc diff` | Сгенерированный код обязан совпадать с запросами в `queries/`. Иначе правка SQL молча не доедет |
| **Секреты в истории** | `gitleaks` | Ключ, попавший в коммит, остаётся в истории навсегда |
| **Известные уязвимости** | `govulncheck` | Не валит сборку: новая запись в базе не должна краснить исправный код |
| **Фронтенд** | `eslint`, `tsc --noEmit`, `vitest`, сборка кабинета и лендинга | Типы и сборка ломаются чаще всего |
| **OpenAPI** | `redocly lint` | Контракт пишется руками, и он расходился с кодом уже трижды |
| **Сборка** | Linux-бинарник | Последняя проверка: собирается ли то, что прошло всё остальное |

Зелёная галочка появится и рядом с коммитом в списке.

## Шаг 7. Дать GitHub доступ к серверу

Нужно только для выката кнопкой из браузера. С вашей машины выкат
работает и без этого:

```bash
ZAPAS_SSH_KEY=~/.ssh/zapas scripts/deploy.sh
```

Settings → Secrets and variables → Actions → **New repository secret**,
три штуки:

| Имя | Значение | Где взять |
|---|---|---|
| `PROD_SSH_KEY` | Приватный ключ целиком, вместе со строками `BEGIN` и `END` | `cat ~/.ssh/zapas` |
| `PROD_HOST` | `85.198.64.102` | — |
| `PROD_USER` | `root` | — |

Ключ уже прописан на сервере в `/root/.ssh/authorized_keys` под именем
`zapas-deploy`, вход по нему проверен.

Секреты нельзя прочитать обратно — только перезаписать. В логах сборки
они заменяются звёздочками.

## Шаг 8. Защитить main

Не обязательно, но отвечает на вопрос «а как у вас устроена работа
с ветками» на собеседовании.

Settings → Branches → **Add branch ruleset** → ветка `main`:

- **Require a pull request before merging** — правки идут через PR;
- **Require status checks to pass** — выбрать работы из шага 6;
- **Do not allow bypassing** — иначе правило не правило.

Учтите: после этого прямой `git push` в `main` перестанет работать,
и придётся заводить ветку и PR:

```bash
git switch -c fix/что-меняем
git push -u origin fix/что-меняем
gh pr create --fill
```

Для проекта, который вы ведёте один, это лишняя церемония. Включайте,
если хотите показать процесс, а не если хотите удобства.

## Шаг 9. Первый выкат кнопкой

Actions → **Deploy** → Run workflow → в поле подтверждения написать
`deploy` → Run.

Слово `deploy` — не украшение: без него работа не запустится вовсе.
Сервер общий с пятью другими проектами, и случайное нажатие не должно
ничего выкатывать.

Что произойдёт: соберётся бинарник и статика, зальются на сервер,
накатятся миграции, перезапустятся сервисы, и проверка дёрнет
`/healthz`, `/readyz`, обе страницы и **каждый скрипт, на который
ссылается кабинет**. Последнее добавлено после того, как прод месяц
отдавал `200` на страницу и `403` на все её файлы.

## Если сборка красная

Открыть работу, развернуть красный шаг — там написано, что именно.
Частые причины:

| Работа | Что говорит | Что делать |
|---|---|---|
| Go — статический анализ | Список файлов и больше ничего | Это `gofmt`. `make fmt`, закоммитить заново |
| Go — статический анализ | `can't load config` | Версия линтера разошлась с форматом `.golangci.yml`. В `ci.yml` она прибита — не заменяйте на `latest` |
| Go — тесты | `connection refused` | Сервисный контейнер не успел подняться, перезапустить работу |
| Go — тесты | Падает один тест | Сначала воспроизвести локально: `make test`. Если локально зелено, а в CI нет — почти всегда время или часовой пояс |
| sqlc | Непустой diff | Забыли `make sqlc` после правки `queries/` |
| Секреты | Найдена находка | **Не переписывать историю в панике.** Сначала отозвать ключ, потом чистить |
| Фронтенд | Ошибка типов | `cd web && npx tsc --noEmit` — тот же вывод локально |
| OpenAPI | Ошибка схемы | `make api-lint` |

Перезапустить работу: **Re-run jobs** в правой верхней части страницы
сборки. Осмысленно только для сетевых отказов; всё остальное
перезапуск не чинит.

## Чего в этом пайплайне намеренно нет

**Автовыката по push в main.** Сервер общий, и решение «выкатываем
сейчас» принимает человек. Для проекта с одним разработчиком
автовыкат экономит минуту и стоит ночи разбирательств.

**Сборки образа и реестра.** Прод работает на systemd, а не в Docker:
на машине с 961 МБ ОЗУ слой контейнеров стоит дороже, чем экономит.
Образ остался для локальной разработки.

**Погони за покрытием.** Ни один дефект проекта не нашёлся бы лишними
процентами. Их находили сквозные тесты, вырожденные данные и открытый
браузер — разбор в [process.md](process.md).
