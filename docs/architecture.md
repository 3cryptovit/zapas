# Архитектура

Модульный монолит на Go: один бинарник в двух рабочих режимах, одна база
PostgreSQL, Redis для очередей (ADR-001).

```
Браузер
  │
  ▼
Nginx ── / и /app ──▶ статика: лендинг и SPA
  │
  └──── /api ───────▶ Go API (chi)
                         ├──▶ PostgreSQL   (два пула: zapas_app и zapas_maint)
                         └──▶ Redis        (очередь asynq, лимиты песочницы)

Go Worker ──▶ Redis ──▶ PostgreSQL ──▶ Telegram Bot API
                                   └─▶ SMTP
```

API обслуживает запросы и ставит задачи в очередь. Worker выполняет
периодические задачи (прогноз, сводки, очистка песочниц) и разгребает outbox.

## Модули

| Модуль | Отвечает за | Зависит от |
|---|---|---|
| `platform` | конфиг, пулы БД, HTTP, логи, метрики, тип `qty.Qty` | — |
| `clock` | `Clock` и календарный день `Day` | — |
| `auth` | сессии, пароли, роли, CSRF | `tenant` |
| `tenant` | тенанты, контекст тенанта, RLS | `platform` |
| `catalog` | позиции, категории, поставщики, импорт CSV | `tenant` |
| `stock` | движения, остатки, инвентаризация | `catalog`, `replenishment` |
| `forecast` | ряды, модели, бэктест — **чистые функции** | `clock`, `qty` |
| `replenishment` | окна поставки, точка заказа, статусы — **чистые функции** | `forecast` |
| `notify` | outbox, сводки, Telegram, email | `tenant` |
| `orders` | заказы поставщику, приёмка | `stock`, `catalog` |
| `dashboard` | read-модель главного экрана и карточки | `replenishment` |
| `sandbox` | генератор данных, симулятор времени, очистка | все |
| `worker` | расписание фоновых задач на asynq | все |

Модуль берёт чужие данные через интерфейс модуля, а не напрямую из его таблиц.
Исключение — запрос дашборда, который собирает экран одним SQL по read-модели
`item_status`.

`forecast` и `replenishment` не знают ни про БД, ни про `time.Now()`: на вход
им подаются готовые структуры, на выход идут числа. Поэтому они покрываются
табличными тестами с заранее посчитанными ответами, а пример из §5.1 и блок
«почему такой статус» из §6.2 лежат в тестах дословно.

## Главный цикл данных

```
Движения ──▶ Остаток (+ в пути) ──▶ Прогноз на 14 дней ──▶ Точка заказа и статус
    ▲                                                              │
    │                                                              ▼
 Приёмка ◀── Заказ «в пути» ◀── Оформление ◀──────── Напоминание (Telegram, лента)
```

Заказ «в пути» входит в позицию запаса, поэтому после оформления повторных
напоминаний по этой позиции нет.

## Ключевые транзакции

### Запись движения (§10.2)

```
BEGIN
  set_config('app.tenant_id', $tenant, true)   -- LOCAL: не протекает через пул
  SELECT id FROM stock_movements WHERE idempotency_key = $key   -- повтор формы
  SELECT on_hand FROM stock_balances ... FOR UPDATE             -- очередь на позицию
  -- on_hand + qty < 0 → ROLLBACK, ответ 409 с текущим остатком
  INSERT INTO stock_movements ...
  UPDATE stock_balances SET on_hand = on_hand + $qty
  -- пересчёт item_status; при ухудшении INSERT в notifications и outbox
COMMIT
```

Блокировка строки остатка превращает конкурентные списания одной позиции
в очередь: отсюда и честная проверка на минус, и отсутствие гонки.
Пересчёт статуса дешёвый (14 чисел прогноза на позицию), поэтому идёт
синхронно в той же транзакции.

### Ночной пересчёт (§4.4)

В 03:00 по времени тенанта: собрать ряд за 90 дней → пересобрать
`daily_consumption` → посчитать модели и бэктест → записать прогноз на 14 дней
и метрики → пересчитать статусы. Задача идемпотентна: повторный запуск за ту же
дату перезаписывает результат.

Внеплановый пересчёт — после импорта CSV и после промотки времени в песочнице.

### Доставка уведомления (ADR-004)

Уведомление пишется в `notifications` и `outbox` в той же транзакции, что
и смена статуса. Воркер забирает пачки `FOR UPDATE SKIP LOCKED`, отправляет,
при ошибке откладывает: 1, 5, 25 минут и далее, до 5 попыток.

## Изоляция тенантов

Четыре уровня, подробно — в [ADR-005](adr/0005-tenant-isolation.md):
приложение берёт `tenant_id` только из сессии, база включает RLS, роль
приложения не владеет таблицами и не обходит RLS, составные внешние ключи
`(tenant_id, id)` не дают связать объекты разных тенантов.

## Время

Всё время берётся через `clock.Clock` (ADR-006). Песочница живёт со смещёнными
часами: `tenants.clock_offset`. День считается в поясе тенанта, а не в UTC.

## Точность чисел

Количества — `numeric(14,3)` в базе и `qty.Qty` (обёртка над `decimal.Decimal`)
в коде. `float64` для количеств запрещён: остаток обязан сходиться с суммой
движений до третьего знака. В JSON количества передаются строками (`"12.500"`),
чтобы их не портил JavaScript.

Внутри `forecast` математика идёт в `float64` — прогноз это оценка, а не
учётная запись; наружу результат выходит уже как `qty.Qty`.


## Фоновые задачи

Воркер держит `asynq.Server` и `asynq.Scheduler`. Логика задач лежит
в обычных методах `worker.Tasks` и про asynq не знает — её можно прогнать
в тесте, не поднимая Redis.

| Задача | Расписание | Что делает |
|---|---|---|
| `notify:outbox` | каждые 30 с | разгребает очередь отправки |
| `forecast:nightly` | каждый час | прогноз у тенантов, у которых сейчас 03:00 |
| `notify:digest` | каждый час | сводка тем, у кого наступило заданное время |
| `notify:cutoff` | каждые 15 мин | напоминание за 2 часа до отсечки |
| `notify:late` | каждый час | алерт о непринятой поставке |
| `stock:reconcile` | ночью | сверка остатков с журналом (FR-17) |
| `sandbox:cleanup` | каждый час | удаление истёкших демо пачками по 20 |

Прогноз и сводка запускаются каждый час, а нужного тенанта задача выбирает
сама: тенанты живут в разных поясах, и «03:00» у каждого своё.

## Пакетные операции

Три места пишут тысячи строк за раз: генератор песочницы (история движений),
ночной пересчёт (дневной расход и прогноз). Все три идут через разворот
массивов `unnest` — один запрос вместо тысяч вставок.

`COPY`, который предполагает §7.1, применить нельзя: PostgreSQL не
поддерживает `COPY FROM` для таблиц с RLS (см. [ADR-005](adr/0005-tenant-isolation.md)).

Создание демо на 38 позициях и 90 днях истории укладывается в 2,4 с
при бюджете 3 с.

## Размещение

ТЗ (§13) предполагало выделенную машину под Docker Compose. Реальный
сервер — общий: 1 vCPU, 961 МБ ОЗУ, 1,9 ГБ свободного диска, и на нём
уже работают пять других проектов, у одного из которых настоящий домен
и настоящие посетители. Отсюда всё остальное.

```
                 Интернет
                     │  HTTPS, Let's Encrypt через nip.io
                     ▼
                  nginx (общий)
        ┌────────────┼─────────────┬──────────────────┐
        ▼            ▼             ▼                  ▼
   /  лендинг   /app/  SPA    /api/  →  8080    /telegram/webhook
                                  │
                        ┌─────────┴──────────┐
                        ▼                    ▼
                   zapas-api            zapas-worker
                   MemoryMax 220M       MemoryMax 260M
                   CPUQuota 60%         CPUQuota 70%
                        │                    │
                        └────────┬───────────┘
                                 ▼
                  PostgreSQL 16 (общий кластер)
                  база zapas, роли owner / app / maint
                                 +
                        Redis (очередь asynq)
```

Три сознательных отступления от ТЗ:

**systemd вместо контейнеров.** На машине с 961 МБ ОЗУ, поделённой
между шестью проектами, слой Docker стоил бы больше, чем экономит.
Юниты получили `MemoryMax` и `CPUQuota` — без них один процесс выдавит
соседние проекты. Образ и `docker-compose.yml` остались для локальной
разработки и CI.

**Существующий кластер PostgreSQL.** Zapas создал свою базу и три роли
(`zapas_owner` — владелец схемы, `zapas_app` — без права обходить RLS,
`zapas_maint` — с правом, для фоновых задач). Чужие базы не затронуты.

**nip.io вместо домена.** Домена у проекта нет, а HTTPS обязателен:
без него Telegram не ставит вебхук. Адрес `zapas.85.198.64.102.nip.io`
резолвится в тот же IP, и Let's Encrypt выдаёт на него обычный
сертификат.

### Наблюдение

Prometheus с Grafana, которые упоминает ТЗ, на этой машине не окупаются.
Вместо них:

- `/metrics` в формате Prometheus на отдельном порту, закрытом снаружи —
  внешний сбор подключается в любой момент без изменений в коде;
- `zapas-watchdog` каждые 5 минут проверяет сервисы, `/readyz`, диск,
  память, затор в очереди уведомлений, расхождение остатков с журналом,
  срок сертификата и свежесть бэкапа. Сообщение уходит в тот же
  Telegram-бот, что и заказы, — и только на переходе «работает →
  сломалось» и обратно, иначе его перестанут читать.

Расхождение остатка с журналом стоит отдельно от остальных проверок:
это не нагрузка, а ошибка в данных. Ночная задача `stock:reconcile`
сверяет их и поднимает `zapas_balance_drift_total`, за которой и следит
сторож.

### Выкат

Бинарник заливается рядом с работающим, миграции накатываются до
подмены, и только после их успеха старая сборка сохраняется в
`app.prev`, а новая занимает её место. Упавшая миграция оставляет прод
на прежней версии; откат кода — копирование `app.prev` обратно.

Отсюда требование к миграциям: **они должны быть совместимы с
предыдущей версией кода**, потому что между накатом схемы и
перезапуском процесса старый код работает с новой схемой.

Порядок действий — в [runbooks/deploy.md](runbooks/deploy.md).
