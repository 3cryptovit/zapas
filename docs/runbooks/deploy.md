# Выкат новой версии

Выкат идёт одной командой и не требует простоя: бинарник подменяется
на месте, systemd перезапускает процесс за пару секунд.

## Способ 1: с машины разработчика

```bash
ZAPAS_SSH_KEY=~/.ssh/zapas scripts/deploy.sh
```

Скрипт собирает linux-бинарник в контейнере `golang:1.26`, собирает
кабинет и лендинг, заливает всё на сервер, накатывает миграции,
перезапускает сервисы и проверяет `/healthz` и `/readyz`.

## Способ 2: из GitHub

Actions → Deploy → Run workflow, в поле подтверждения написать `deploy`.

Нужны секреты репозитория: `PROD_SSH_KEY`, `PROD_HOST`, `PROD_USER`.

## Что происходит внутри

Порядок шагов выбран так, чтобы неудача на любом из них не оставила
прод в полурабочем состоянии:

1. Новый бинарник заливается как `app.new` — работающий `app` не тронут.
2. Накатываются миграции. **Если они падают — выкат останавливается
   здесь**, и прод продолжает работать на прежней версии.
3. Текущий `app` копируется в `app.prev` (это и есть запас для отката).
4. `app.new` переименовывается в `app`.
5. `systemctl restart zapas-api zapas-worker`.
6. Проверяются `/healthz` и `/readyz`.

Отсюда следует главное правило про миграции: **они должны быть
совместимы с предыдущей версией кода**. Между шагом 2 и шагом 5
старый код работает с новой схемой. Поэтому колонку сначала добавляют,
и только следующим релизом — перестают писать в старую.

## Проверка руками после выката

```bash
curl -s https://vitalness.ru/zapas/readyz
curl -o /dev/null -w '%{http_code}\n' https://vitalness.ru/zapas/app/
journalctl -u zapas-api -n 30 --no-pager | grep -i error
```

Если локальный DNS за VPN, добавьте `--resolve vitalness.ru:443:85.198.64.102`:
VPN в режиме fake-ip отвечает подменным адресом из 198.18.0.0/15.

И зайти в кабинет: дашборд должен открыться и показать позиции.

## Если что-то пошло не так

- **Миграция упала.** Прод не пострадал, он на старой версии. Чините
  миграцию и выкатывайте заново.
- **Сервис не поднялся.** `journalctl -u zapas-api -n 50 --no-pager`.
  Чаще всего — опечатка в `/etc/zapas/zapas.env` или недоступная БД.
- **Поднялся, но работает неправильно.** См. [rollback.md](rollback.md).

## Конфиг nginx выкатывается отдельно

`scripts/deploy.sh` намеренно не трогает nginx: на этой машине его
конфиг общий с пятью другими проектами, и менять его должен человек,
а не скрипт.

Zapas живёт на `vitalness.ru/zapas/` и своего `server` не имеет.
Сервер `vitalness.ru` принадлежит репозиторию портфолио, а Zapas
поставляет только свои `location`:

| В репозитории | На сервере |
|---|---|
| `deploy/nginx/zapas.conf` | `/etc/nginx/snippets/zapas.conf` |

Файл подключается строкой `include /etc/nginx/snippets/zapas.conf;`
в `/etc/nginx/sites-available/vitalness`. Сам по себе он ничего не
включает: загрузка под другим именем молча не применяется.

Порядок:

```bash
tr -d '\r' < deploy/nginx/zapas.conf |
  ssh root@85.198.64.102 'cat > /tmp/zapas.snippet'

ssh root@85.198.64.102 'set -e
  dst=/etc/nginx/snippets/zapas.conf
  cp -p "$dst" /tmp/zapas.snippet.prev
  install -m 644 /tmp/zapas.snippet "$dst"
  if nginx -t; then
    systemctl reload nginx
  else
    install -m 644 /tmp/zapas.snippet.prev "$dst"
    echo "конфиг сломан, вернул прежний"
    exit 1
  fi'
```

`tr -d '\r'` — потому что файл с Windows может приехать с CRLF: nginx
его переварит, но `diff` с живым конфигом станет бесполезен.

`nginx -t` до `reload` обязателен, и откат встроен в ту же команду:
битый конфиг положит не только Zapas, но и свадебный сайт с настоящими
посетителями. После — проверьте соседей:

```bash
ssh root@85.198.64.102 'for d in vadim-lubov-wedding.ru vitalness.ru; do
  echo "$d $(curl -s -o /dev/null -w "%{http_code}" -k --resolve "$d:443:127.0.0.1" "https://$d/")"
done'
```

## Чего не делать

- Не редактировать уже применённую миграцию. Накатите новую.
- Не выкатывать правку конфига nginx без `nginx -t`.
- Не делать `systemctl restart nginx` — только `reload`, иначе упадут
  соседние проекты.
