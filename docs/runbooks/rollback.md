# Откат

Выкатили, и стало хуже. Задача — вернуть работающую версию за минуту,
а разбираться потом.

## Сначала ответьте на один вопрос

**Были ли в этом выкате миграции?**

```bash
set -a; . /etc/zapas/zapas.env; set +a
/srv/zapas/bin/app migrate status 2>&1 | tail -5
```

Если последняя применённая миграция появилась только что — были.
От ответа зависит всё остальное.

## Случай 1: миграций не было

Самый частый и самый простой.

```bash
cp -p /srv/zapas/bin/app.prev /srv/zapas/bin/app
systemctl restart zapas-api zapas-worker
sleep 3
systemctl is-active zapas-api zapas-worker
curl -s https://vitalness.ru/zapas/readyz
```

Занимает секунд десять. `app.prev` — это бинарник, работавший до
выката; его сохраняет сам скрипт деплоя.

## Случай 2: миграции были

Здесь нельзя действовать наугад: откат схемы может стоить данных.

**Сначала попробуйте откатить только код.** Миграции пишутся
совместимыми с предыдущей версией (см. [deploy.md](deploy.md)),
поэтому старый бинарник с новой схемой обычно работает:

```bash
cp -p /srv/zapas/bin/app.prev /srv/zapas/bin/app
systemctl restart zapas-api zapas-worker
curl -s https://vitalness.ru/zapas/readyz
```

Если заработало — остановитесь на этом. Схему откатывать не нужно.

**Если не заработало** и дело точно в схеме — учтите главное:

```
$ app migrate down
migrate down в проде запрещён: откат делается новой миграцией
```

Это не поломка, а намеренное ограничение. `down`-миграции пишутся
для локальной разработки и почти никогда не проверяются на реальных
данных; выполнять непроверенный `DROP` на живой базе в разгар аварии —
верный способ превратить сбой в потерю данных.

Поэтому в проде есть ровно два пути:

**Путь А — исправляющая миграция (предпочтительный).** Пишется новая
миграция, которая приводит схему в рабочее состояние, и выкатывается
обычным деплоем. Это дольше на несколько минут, но каждое действие
проходит ревью и остаётся в истории.

**Путь Б — восстановление из бэкапа.** Когда миграция успела испортить
данные и починить их запросом нельзя. Порядок — в
[restore.md](restore.md). Учтите: вернётся состояние на момент ночного
дампа, всё, что внесли после, будет потеряно. Поэтому сначала
снимите дамп текущего состояния — из него потом можно достать
недостающее:

```bash
/srv/zapas/bin/backup.sh
```

## Случай 3: сломался не код, а nginx или сертификат

```bash
nginx -t                       # покажет, где ошибка
systemctl reload nginx         # именно reload
```

Конфиг Zapas — `/etc/nginx/sites-available/zapas.conf`. Если его
сломали, худшее, что можно сделать, — `systemctl restart nginx` с
битым конфигом: nginx не поднимется, и упадут все пять проектов
на машине. `nginx -t` до перезагрузки конфига обязателен.

## После отката

1. Убедитесь, что кабинет открывается и дашборд показывает данные.
2. Сохраните логи упавшей версии, пока их не вытеснило:
   ```bash
   journalctl -u zapas-api --since '30 min ago' --no-pager > /tmp/incident.log
   ```
3. Запишите, что произошло, в `docs/journal.md` — следующий раз начнётся
   с чтения этой записи.
