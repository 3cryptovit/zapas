# ADR-005. Изоляция тенантов: tenant_id, RLS и составные внешние ключи

Статус: принято · 19.09.2026

## Контекст

Песочница делает систему публичной: любой посетитель лендинга получает свой
тенант одной кнопкой. Утечка данных между тенантами — самый дорогой отказ,
какой здесь возможен, а защищаться приходится от собственных будущих ошибок
в SQL.

## Решение

Четыре уровня, каждый ловит то, что пропустил предыдущий (§12.1).

1. **Приложение.** `tenant_id` берётся только из сессии, никогда из тела
   запроса или URL. Каждый метод репозитория принимает его явным аргументом.
2. **База.** RLS включён на всех таблицах с `tenant_id`. Политика:
   `tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid`.
   Без заданного тенанта сравнение даёт NULL и не проходит ни одна строка.
   `WITH CHECK` в той же политике не даёт записать строку чужому тенанту.
3. **Роли.** Приложение работает под `zapas_app`: не владеет таблицами и
   не имеет BYPASSRLS, поэтому политики на неё действуют. Миграции идут от
   `zapas_owner`, а обслуживание — от `zapas_maint` с BYPASSRLS.
4. **Ссылки.** Составные внешние ключи `(tenant_id, id)` не дают связать
   объекты разных тенантов даже при ошибке в коде.

Тенант выставляется через `set_config('app.tenant_id', $1, true)` — это
параметризованный аналог `SET LOCAL`. Именно `LOCAL`: значение живёт до конца
транзакции и не протекает в следующий запрос через пул соединений.

## Где нужен BYPASSRLS

Есть запросы, в которых тенант ещё не известен: вход по email, разбор сессии
по хешу токена, обход тенантов ночными задачами и удаление истёкших песочниц.
Они идут через отдельный пул под ролью `zapas_maint`. Список таких мест
намеренно короткий и растёт только осознанно.

## Последствия

- Забытый `WHERE tenant_id = $1` перестаёт быть уязвимостью: строку не отдаст
  база.
- Каждое обращение к данным клиента обязано быть внутри транзакции.
- Два пула соединений вместо одного.
- Планировщик учитывает предикат политики; отсюда требование, чтобы `tenant_id`
  стоял первым в составных индексах.

## Проверка

`migrations/20260919090600_rls.sql` плюс интеграционный тест: два тенанта,
проход по всем эндпоинтам, пользователь A получает 404 на любой ресурс B;
отдельный тест выполняет запросы без тенанта и ожидает ноль строк.

## Что RLS ломает

`COPY FROM` на таблице с включённым RLS PostgreSQL не поддерживает
(`0A000: COPY FROM not supported with row-level security`). Генератору
песочницы это важно: в §7.1 история пишется именно COPY-ем.

Обходим разворотом массивов — один запрос вместо тысяч вставок:

```sql
INSERT INTO stock_movements (...)
SELECT ... FROM (
    SELECT unnest($1::uuid[]) AS item_id,
           unnest($2::numeric[]) AS qty, ...
) AS m;
```

Скорость та же — один заход в базу, — а политика проверяется как на
обычном INSERT. Отключать RLS ради генератора мы не стали: тогда пришлось бы
держать отдельный путь записи, который никто не проверяет тестами изоляции.

## Отвергнуто

**Схема или база на тенанта.** При тысячах демо-тенантов это тысячи схем,
неподъёмные миграции и разъезжающийся пул соединений.
