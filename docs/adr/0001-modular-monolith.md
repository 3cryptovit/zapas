# ADR-001. Модульный монолит вместо микросервисов

Статус: принято · 19.09.2026

## Контекст

Система состоит из склада, прогноза, правил заказа, уведомлений и песочницы.
Модули связаны: статус позиции пересчитывается в той же транзакции, что и
движение, а уведомление пишется в outbox вместе со сменой статуса. Проект ведёт
один разработчик, деплой — один VPS на 2 vCPU и 4 ГБ.

## Решение

Один бинарник `cmd/app` в четырёх режимах: `api`, `worker`, `migrate`, `seed`.
Модули живут в `internal/*` и общаются через интерфейсы, а не через таблицы
друг друга. Единственное исключение — запрос дашборда, который собирает экран
одним SQL по read-модели `item_status`.

## Последствия

- Транзакция «движение → остаток → статус → outbox» остаётся одной транзакцией
  БД. В микросервисах здесь понадобилась бы сага.
- Локальный запуск — одна команда, в CI поднимается тот же compose.
- Масштабирование только вертикальное. Для 1–5 точек на тенанта этого хватает
  с запасом; при необходимости `worker` уже отделяется от `api` без изменений
  в коде.
- Границы модулей приходится держать дисциплиной, а не сетью. Правило
  «не ходить в чужие таблицы» вынесено в CONVENTIONS.md.

## Отвергнуто

**Микросервисы.** Для такого объёма добавили бы очередь между складом и
прогнозом, распределённые транзакции и пять Dockerfile — без единого выигрыша.
